## 一、目标

打开开关后，工具盯着微信当前聊天：**对方发来新消息 → 按这个人的风格生成回复 → 回填输入框 → 自动发送**。

只在白名单里、且单独打开了该联系人开关的人身上生效。

### 不做

- 不接管多个聊天窗口（只处理当前打开的那个）
- 群聊默认禁止（见 §4.5）
- 不主动发起对话（只回应）
- 不保存聊天与回复正文到日志

---

## 二、两级控制模型

```
总开关（全局）
   │  关 → 任何人不回（但热键润色照常可用）
   ▼
每人一条规则
   ├─ 五味子   [开]  风格：通用润色   → 自动回复
   ├─ 王斌     [关]  风格：亲切友好   → 不回复（配置保留）
   └─ 李四     [开]  风格：毒舌回怼   → 自动回复（小心）
```

判定顺序：`总开关 → 会话名匹配到白名单项 → 该项 enabled → 静默/限流 → 各项安全校验`。

**任何一环不满足都不动作**，日志里写明是哪一环拦下的（便于排查"为什么没回"）。

---

## 三、核心流程

```
调度线程每 interval 秒醒一次
   ▼
① 微信窗口存在吗？              ← 否：跳过
   ▼
② 抓窗口帧 → 定位 → OCR        ← 复用 capturer.read_wechat_recent_with_title
   ▼
③ 会话名命中白名单且 enabled？   ← 否：跳过（不调模型，不花钱）
   ▼
④ 消息指纹与上次相同？           ← 是：跳过（省掉整轮成本）
   ▼
⑤ 最后一条是"对方"发的？         ← 否（是我发的）：跳过，防自问自答
   ▼
⑥ 这条消息已回复过？             ← 是：跳过（指纹去重）
   ▼
⑦ 静默时段 / 每小时条数超限？     ← 超限：跳过 + 托盘提示
   ▼
⑧ 调模型（reply 模式，最近 N 条上下文，用该联系人的提示词）
   ▼
⑨ 随机延迟 20~90 秒
   ▼
⑩ 发送前四道闸（§4）            ← 任一不通过：放弃，写日志
   ▼
⑪ 回填 → 模拟回车 → 等 1.5s → 自己的回复记入已回复集合
```

## 四、自动发送的四道闸（核心安全设计）

发出去就撤不回，所以每次发送前逐条校验，任一不过就放弃：

### 闸 1 · 会话没变

重新读一次当前会话名，必须与生成时一致。期间你切了会话 → 放弃。

### 闸 2 · 输入框是空的

你可能正在打字。发送前读输入框（`capturer.capture_draft()`）：

- 非空 → **放弃**，绝不覆盖你正在写的东西
- 空 → 继续

### 闸 3 · 窗口在前台且可交互

模拟键盘需要焦点。微信在后台/最小化时默认**放弃**（不抢焦点）；
可选开启「允许短暂激活窗口」（`activate_window`，默认 `false`），见 §7.3。

### 闸 4 · 内容自检

生成结果必须同时满足：

- 非空、长度 ≥ 2
- 不等于对方刚发来的原文（防复读）
- 不含 `[[`、`{"`、"提示词" 这类泄露痕迹
- 不含"作为 AI"、"我无法"等自我暴露语句

不过 → 放弃并记录，本轮不重试（避免死循环）。

### 4.5 群聊

`group_enabled` 默认 `false`。群里自动回复的风险是回错人 + 刷屏，开启需二次确认。

### 4.6 发送之后

- 不额外抓帧确认（成本高，且自己的消息会污染指纹）
- 发送后 1.5 秒内把自己的回复文本记入已回复集合，避免下一轮当成新消息触发
- 连续失败 3 次 → 自动关闭总开关 + 托盘告警

## 五、配置结构

```json
"auto_reply": {
  "enabled": false,
  "contacts": [
    { "name": "五味子", "enabled": true,  "prompt_id": "builtin_general" },
    { "name": "王斌",   "enabled": false, "prompt_id": "builtin_friendly" }
  ],
  "group_enabled": false,
  "interval_sec": 60,
  "context_messages": 10,
  "reply_delay_sec": [20, 90],
  "max_per_hour": 10,
  "quiet_hours": ["22:00", "08:00"],
  "auto_off_after_min": 120,
  "activate_window": false,
  "dry_run": false
}
```

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | false | 总开关 |
| `contacts[].name` | — | 微信显示名，精确匹配 |
| `contacts[].enabled` | false | 该联系人是否自动回复 |
| `contacts[].prompt_id` | `null` | 回复风格；`null` = 跟随「联系人规则」，再没有就用全局当前提示词 |
| `group_enabled` | false | 群聊开关 |
| `interval_sec` | 60 | 轮询间隔（30/60/120） |
| `reply_delay_sec` | [20,90] | 生成后随机等待，避免秒回 |
| `max_per_hour` | 10 | 每人每小时上限 |
| `quiet_hours` | 22:00~08:00 | 静默时段，跨零点支持 |
| `auto_off_after_min` | 120 | 开启后自动关闭，0 = 不自动关 |
| `activate_window` | false | 是否允许短暂激活微信窗口（§7.3） |
| `dry_run` | false | 调试模式：只走流程写日志，不真的发送 |

> 与现有 `contact_rules` 的关系：`contact_rules` 管「手动按热键时用哪条提示词」；
> `auto_reply.contacts[].prompt_id` 可覆盖它，留空则继承。两处不冲突，也不用重复填。

## 六、交互设计

### 6.1 设置页「自动回复」页签

```
┌─ 自动回复 ────────────────────────────────────┐
│  [✓] 启用自动回复     已运行 12 分钟  [暂停10分钟] │
│                                                │
│  回复对象                                       │
│  ┌──────────────────────────────────────────┐ │
│  │ [✓] 五味子      风格 [通用润色      ▾]  ✕ │ │
│  │ [ ] 王斌        风格 [跟随联系人规则 ▾]  ✕ │ │
│  └──────────────────────────────────────────┘ │
│  [+ 从当前会话添加]                             │
│                                                │
│  轮询 [60 秒 ▾]   上下文 [10 条]               │
│  生成后等待 [20] ~ [90] 秒                      │
│  每小时最多 [10] 条                             │
│  静默时段 [22:00] ~ [08:00]                    │
│  开启后 [120] 分钟自动关闭                      │
│  [ ] 允许短暂激活微信窗口（不在前台时也能发）    │
│  [ ] 调试模式（只记录不发送）                   │
└────────────────────────────────────────────────┘
```

- 每行独立复选框 = 该联系人的开关
- 风格下拉含 7 条内置（含毒舌/舔狗）+ 自定义项 + 「跟随联系人规则」
- 「从当前会话添加」自动读取当前微信会话名，省得手打

### 6.2 状态提示（自动发送必须让人时刻知道它在工作）

- 托盘图标加红点 / 变色
- 悬停：`自动回复中 · 五味子 · 今日已回 3 条 · 下次 12s`
- 托盘菜单第一项：`暂停自动回复（10 分钟）`
- 每次成功发送，小搭气泡只显示「已回复 五味子」，**不显示内容**

## 七、技术方案

### 7.1 模块划分

| 文件 | 改动 |
|---|---|
| `auto_reply.py` | **新增**：`AutoReplier` 调度器（线程、指纹、限流、静默、状态上报） |
| `sender.py` | **新增**：`send_enter(hwnd)` + `can_send(hwnd, expected_title)` 四道闸校验 |
| `config.py` | 新增 `auto_reply` 默认值 + 校验（时间格式、延迟区间、间隔下限） |
| `config_editor.py` | 新增页签（每联系人开关 + 风格下拉） |
| `main.py` | 创建/停止调度器，注册开关回调 |
| `tray_widget.py` | 状态标识 + 暂停菜单 |
| `paste_back.py` | 不动（只负责粘贴），发送逻辑独立成 `sender.py` |

复用：`read_wechat_recent_with_title`（抓取 + 会话名）、`capture_draft`（读输入框）、
`ai_client.build_messages(mode="reply")`、`find_wechat_hwnd`。

### 7.2 指纹与去重

```python
fp = md5(会话名 | 最后一条(说话人, 文本) | 消息条数)
```

- 与上次相同 → 本轮跳过
- 已回复集合保留最近 20 条，持久化到 `auto_reply_state.json`（重启后不重复回）

### 7.3 焦点问题（必须提前定）

模拟键盘要求微信有焦点，三种策略：

| 策略 | 行为 | 代价 |
|---|---|---|
| **A 不抢焦点**（默认） | 微信不在前台就跳过本轮 | 你一切走它就不回，可能"该回没回" |
| **B 允许激活** | 短暂激活微信 → 发送 → 尽量切回原窗口 | 会打断你正在做的事，切回也可能失败 |
| **C UIA 直写** | 直接向输入框控件写文本 | 微信 4.x 的 Qt 界面不响应 SetValue，不可靠 |

默认 A + 可选 B。**这条决定"能不能真无人值守"**，见 §十一。

### 7.4 线程与资源

- 调度线程 daemon，异常就地捕获；连续失败 3 次自动关开关
- OCR 引擎与热键共用 → 加互斥锁（RapidOCR 非线程安全）
- 空闲单周期开销：一次抓帧 + 一次 OCR（约 2.4s），CPU 峰值 20% 内

## 十、验收标准

| 项 | 标准 |
|---|---|
| 触发 | 白名单内且开关打开的联系人来消息，一个周期 + 随机延迟内完成发送 |
| 不误回 | 非白名单 / 该人开关关闭 / 群聊未开 / 静默时段 / 最后一条是我发的 → 均不动作 |
| 不重复 | 同一条只回一次，重启后仍生效 |
| 不覆盖 | 输入框有草稿时不发送 |
| 不误发 | 会话名不匹配、窗口不在前台（策略 A）时拒绝并写日志 |
| 可停止 | 关开关后下一周期立即停；线程干净退出 |
| 隐私 | 日志只有会话名、动作、耗时、拦截原因，**无正文** |

## 十三、风险与合规

### 技术上为什么相对安全

三种常见实现，微信能看到的程度差一个量级：

| 方式 | 微信能看到什么 | 风险 |
|---|---|---|
| 协议 / 逆向（hook 客户端、改协议包、第三方登录） | 客户端被动过手脚 | **极高，基本必封** |
| 模拟点击（直接 SetValue 写控件） | 有程序在操作 | 中 |
| **本工具**：截屏 OCR 看字 + 剪贴板粘贴 + 模拟回车 | 和真人键盘输入一样 | 低 |

不读微信内存、不修改客户端、不走私有协议，所以不会触发客户端完整性检测——
而那是封号概率最高的一条线。

### 真正的风险不在封号

1. **行为特征太规律**：固定 20~90 秒内必回、24 小时不间断。真人不会这样，
   凌晨三点也秒回，一周下来行为画像很难看。
2. **内容出问题被举报**：给客户发了一句不该发的风格，或群聊里刷屏——
   这属于内容违规，处罚比"用了工具"重得多。

微信用户协议确实禁止"使用外挂或自动化工具"，理论上都违规。但实际处罚优先级大致是：
协议机器人 > 高频营销群发 > 模拟输入类工具。

### 建议配置

| 项 | 建议 | 原因 |
|---|---|---|
| 静默时段 | 至少 `22:00 ~ 08:00` | 半夜秒回是最明显的机器特征 |
| 每小时上限 | 5 条以内 | 正常聊天一小时说不了 10 轮 |
| 白名单 | 只放同事和朋友 | 不是怕封号，是怕说错话 |
| 群聊 | 保持关闭 | 群里刷屏最容易被举报 |
| 回复风格 | 别给客户/领导用毒舌、舔狗 | 风格类提示词偏移大，容易失控 |
| 巡检 | 每周看一次日志的「已回复 xxx」 | 确认没在你不知道的时候乱说话 |

**一句话结论：封号概率不高，说错话概率不低。**
白名单和回复风格这两项，比任何技术参数都重要。
