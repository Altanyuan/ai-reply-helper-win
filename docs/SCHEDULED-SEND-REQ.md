## 1. 功能范围

### 1.1 做什么

- 新建任务：指定「发给谁」「发什么」「什么时候发」
- 两种时间：**每天固定时刻**（可限定周几）、**未来某一时刻**（只执行一次）
- 到点自动：激活微信 → 搜索这个人 → 校验会话 → 输入内容 → 发送 → 校验气泡
- 执行前可「试一次」：完整走流程但停在输入框，截图给你确认，不按回车
- 失败可见：日志 + 托盘告警，连续失败 3 次自动停用该任务

### 1.2 不做什么

- 群聊、@ 成员（配置结构留了 `type` 字段，但 UI 只开放"好友"）
- 批量发给多人（一次任务只发一个人）
- 内容变量（`{date}` 这类占位符）
- 条件触发（"某人 3 天没说话就发一句"）
- cron 表达式

## 2. 任务模型

### 2.1 两种类型

| 类型 | `kind` | 时间字段 | 执行后 |
|---|---|---|---|
| 每天 | `daily` | `time: "09:00"` + `days: [1..7]` | 记录 `last_run`，第二天继续 |
| 一次性 | `once` | `at: "2026-11-25 09:00"` | 更新 `last_run`，不再执行 |

`days` 为空数组 = 每天；`[1,2,3,4,5]` = 工作日（1=周一）。

### 2.2 字段表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | `t_` + 8 位随机，创建后不变 |
| `name` | str | 任务名（只用于界面显示） |
| `enabled` | bool | 是否启用 |
| `kind` | `"daily"` / `"once"` | 见上 |
| `time` | `"HH:MM"` | daily 用 |
| `days` | list[int] | daily 用；空 = 每天 |
| `at` | `"YYYY-MM-DD HH:MM"` | once 用 |
| `target` | str | 微信显示名，精确匹配（归一化后比较） |
| `type` | `"friend"` | 目前只允许 friend |
| `text` | str | 发送内容，支持多行 |
| `verified` | bool | 是否已通过「试一次」。**未验证不允许启用** |
| `last_run` | str | `"YYYY-MM-DD HH:MM"`，防重复用 |
| `fail_count` | int | 连续失败次数，到 3 自动停用 |
| `last_result` | str | `成功` / `失败：<原因>`，界面显示用 |

### 2.3 配置示例

```json
"scheduled": {
  "enabled": true,
  "scan_sec": 20,
  "catch_up_min": 0,
  "restore_focus": true,
  "tasks": [
    {

      "name": "给五味子发早报",
      "enabled": true,

      "target": "五味子",

      "verified": true,
      "last_run": "2026-11-24 09:00",
      "fail_count": 0,
      "last_result": "成功"
    },
    {
      "id": "t_91c2b4de",
      "name": "提醒王斌交材料",
      "enabled": true,
      "kind": "once",
      "time": "",
      "days": [],
```

### 2.4 状态流转

```
         新建
           │
           ▼
     verified=false ──(试一次成功)──► verified=true
           │                              │
           │                        (启用开关打开)
           │                              ▼
           └──────────────────────► 等待中(pending)
                                          │
                                    到点触发
                                          ▼
                                      执行中(running)
                                          │
                        ┌─────────────────┴─────────────────┐
                        ▼                                   ▼
                   执行成功                              执行失败
                        │                                   │
            daily: 记 last_run, 回 pending        fail_count += 1
            once:  记 last_run, 自动停用           │
                                                    ├─ <3：回 pending
                                                    └─ =3：自动停用 + 告警
```

## 3. 调度逻辑

### 3.1 扫描与判定

调度线程每 `scan_sec`（默认 20 秒）醒一次：

```python
now = datetime.now()
for task in tasks:
    if not task.enabled or not task.verified:
        continue
    if task.kind == "daily":
        if task.days and now.isoweekday() not in task.days:
            continue
        if (now.hour, now.minute) >= (H, M) and not ran_today(task, now):
            trigger()
    else:  # once
        if now >= parse(task.at) and task.last_run == "":
            trigger()
```

**精度**：最坏延迟 `scan_sec` 秒（20 秒）。对"9 点发早安"足够；不需要秒级。

### 3.2 错过补偿（重要）

程序在 09:00 时没运行（关机/退出），10:30 才启动——要不要补发？

| 策略 | 行为 |
|---|---|
| `catch_up_min: 0`（默认） | **不补**。错过就跳过，今天算了 |
| `catch_up_min: 30` | 迟到 30 分钟内补发，超过则跳过 |

为什么默认不补：「早上好」10 点半发很怪；「提醒交材料」迟到一点没事。这个值留给用户调。

启动时会把"今天已经过了时间但没跑"的任务标为 `已跳过（错过时间）`，不发。

### 3.3 防重复

三重保险：

1. `last_run` 记录到分钟，`ran_today()` 判断日期相同即跳过
2. 执行期间任务状态置 `running`，扫描时跳过 `running`
3. 整个执行过程持有「微信操作锁」，扫描线程不会并发触发第二个任务

### 3.4 与自动回复互斥

自动回复也在操作微信。两者共用一把 `wechat_lock`（`threading.Lock`）：

- 定时任务到点先 `acquire(blocking=False)`
- 拿不到 → 记「微信正被自动回复占用，30 秒后重试」，最多重试 3 次（共 90 秒），仍失败则本次作废并记录
- 反向也一样：自动回复的 `_tick` 也要先拿这把锁

这是本次要改 `auto_reply.py` 的唯一地方（加锁的 acquire/release）。

### 3.5 时钟与跨天

- 全部用本机 `datetime.now()`，不依赖时区库
- 跨天判断只看 `date()`，不看 `datetime` 差
- 用户改系统时间导致"倒退"时，`last_run` 的日期可能在未来 → 当天不执行（安全的失败方向）
- once 任务的 `at` 若早于当前时间 → 新建时直接拒绝（"时间已过"）

## 4. 执行流程（逐步，含失败分支）

| # | 步骤 | 校验 | 失败处理 | 典型耗时 |
|---|---|---|---|---|
| 1 | 拿 `wechat_lock` | 非阻塞获取 | 重试 3×30s，仍失败 → 本次作废 | 0 |
| 2 | 微信进程在吗 | `find_wechat_hwnd()` | 失败 → 记「微信未运行」，本次作废 | 0.1s |
| 3 | 激活窗口 | `unminimize()` + `SetForegroundWindow` | 失败重试 1 次 | 0.5s |
| 4 | 当前会话是不是目标 | 读标题栏（WGC + OCR） | 是 → 跳到第 9 步 | 2.5s |
| 5 | 点搜索框 → 输入名字 | 回读搜索框含关键词 | 不含 → 唤醒微信后重试 1 次 | 1.5s |
| 6 | 解析结果面板 | 按分区挑「联系人」条目 | 无候选 / 多个同名 → **失败退出** | 1.5s |
| 7 | 点击进入会话 | 读标题栏 == 目标 | 不等 → 失败退出（防发错人） | 1.5s |
| 8 | 清空输入框 | 读输入框为空 | 非空 → `Ctrl+A` 后再清一次 | 0.5s |
| 9 | 输入正文 | — | — | 0.4s |
| 10 | 回读输入框核对 | 前 20 字必须命中 | 不符 → 失败退出（**不发**） | 1.5s |
| 11 | 回车发送 | — | — | 0.2s |
| 12 | 回读气泡确认 | 前缀探针（4~8 字）命中聊天区 | 未命中 → 等 1.6s 再看一次；仍无 → 记「已发送但未确认」 | 3s |
| 13 | 恢复焦点（可选） | — | 失败忽略 | 0.4s |

**总耗时约 12~15 秒**（主要是 3 次 OCR，各约 2.5 秒）。

关键点：**第 10 步是最后一道闸**——输入框内容对不上就不按回车。宁可这次不发，也不发错内容。

## 5. 关键技术实现

### 5.1 搜索框定位

微信 4.x 左侧会话栏顶部有搜索框。不写死坐标，用两步：

1. 用 `capture_wgc.chat_area()` 得到会话列表右边界 `list_right`（这次已修好，稳定在 340 左右）
2. 搜索框中心 ≈ `(list_right * 0.5, 窗口高 * 0.068)`

点击前不校验位置，点击后靠第 5 步的"回读搜索框"确认点对了。

### 5.2 结果面板解析（移植 wxsend.py 的做法）

```python
# 1. OCR 整个左栏
items = ocr(left_region)

# 2. 找出分区标题（联系人 / 群聊 / 聊天记录 / 收藏 / 公众号 / 功能）
headers = [(section_of(t), y) for t in items if section_of(t)]

# 3. 每个结果归属到「离它最近且位于它上方」的标题
# 4. 只保留 section == "联系人" 的候选
# 5. 排序：精确 > 前缀 > 包含；同级取最靠上
# 6. 多个「精确同名」→ 直接失败，不猜
# 7. 只有「包含」级匹配 → 也失败（定时任务没有人工确认，不能模糊）
```

跟 wxsend 的差异：**去掉 `--fuzzy` 出口**。命令行脚本有 `--fuzzy` 是因为人在旁边看着；定时任务无人值守，模糊匹配等于赌博。

### 5.3 会话校验

读标题栏，与 `target` 做归一化比较（NFKC + casefold，跟自动回复同一套）：

```python
normalize_name(标题) == normalize_name(task.target)
```

不等 → 放弃。这是防发错人的最后一道。

### 5.4 输入与清空

- 清空：点输入框 → `Ctrl+A` → `Delete`（比直接覆盖更干净，避免残留尾巴）
- 输入：`paste_back(text)`（本身会覆盖，前面已清空是双保险）
- 多行文本：`paste_back` 直接粘贴，微信输入框支持换行

### 5.5 发送与确认

- 回车发送
- 若发送后输入框仍有文字 → 说明是 Ctrl+Enter 模式 → 补一次 `Ctrl+Enter`
- 气泡确认：取聊天区 OCR 文本，用正文前 4~8 个字做前缀探针（OCR 常漏气泡末字）

「已发送但未确认」不算失败（消息可能已经发出去了），但要在日志和 `last_result` 里标出来。

### 5.6 焦点恢复

执行完 `SetForegroundWindow(原窗口)`。定时任务一定抢了焦点，还回去体验好些。
失败就忽略（Windows 前台锁定策略有时会拒绝）。

## 8. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 抢焦点打断用户 | 到点弹出微信 | 已确认接受；执行完恢复原窗口；界面显著说明 |
| 发错人（同名/改名） | 不可撤回 | 分区筛选 + 精确匹配 + 会话名校验；不一致直接放弃 |
| 内容发错（输入被吞） | 发出半句话 | 第 10 步回读核对，不符就不按回车 |
| 错过时间 | 该发没发 | `catch_up_min` 可配；默认跳过并在结果里标注 |
| 重复发送 | 同一句发两次 | `last_run` + `running` 状态 + 全局锁 |
| 与自动回复打架 | 两个线程同时操作微信 | 共用 `wechat_lock` |
| 微信卡死/未登录 | 任务失败 | 失败 3 次停用 + 托盘告警 |
| 无人值守时出错没人管 | 几小时后才发现 | 托盘气泡提示失败；`last_result` 在列表可见 |

## 12. 还需要你确认 3 件事

1. **错过时间要不要补发？**
   默认不补（`catch_up_min: 0`）。比如 9 点的早安，10 点开机就不发了。要补就给个窗口（比如 30 分钟）。

2. **「先试一次才能启用」这条硬性要求，保留吗？**
   我建议保留。定时任务无人值守，发错没法撤回；代价是每建一个任务都要多操作一步。

3. **执行完恢复焦点，默认开还是关？**
   开：执行完回到原来的窗口，但画面会闪一下。
   关：停在微信界面，你得自己切回去。
   我建议开。
